## 2. 贴图体积与格式

`buildTextures()` 里画完直接塞进 `TEX`，渲染时 `drawImage`。

| 贴图键 | 画布尺寸 | 格式 | 用途 |
| --- | --- | --- | --- |
| `TEX.floor` | **1216×896** | RGBA8888 | 地面（1 纹素 = 1 世界像素，永远 1:1） |
| `TEX.wall` | 256×128 | RGBA8888 | 墙面（竖向拼缝 + 中缝 + 锈迹）平铺 |
| `TEX.wood` | 128×128 | RGBA8888 | 木箱 / 桶身 / 台面 |
| `TEX.metal` | 128×128 | RGBA8888 | 铁箍 / 箱扣 / 工具箱 / 台腿 |
| `TEX.gold` | 128×128 | RGBA8888 | 金面（祭坛顶层、楼梯踏步） |
| `TEX.stone` | 96×96 | RGBA8888 | 断柱 / 碎石 / 石座 |
| ~~`TEX.corridor`~~ | ~~128×128~~ | — | **本轮不生成**（`SHOW_DOORS = false` 时跳过） |

| 指标 | 值 | 口径 |
| --- | --- | --- |
| 未压缩总量 | **4612 KB raw** | 6 张画布 `宽×高×4` 求和（`?dump=stats` 的 `texRawKB`） |
| PNG 压缩后 | **约 1301 KB** | 每张 `toDataURL('image/png')` 实际字节求和，用来估预烘焙文件的体积 |

## 3. 加载方式（两条路，选一条）

### 路线 A：移植代码（推荐）

跟主文件现有的 `bakeScene()` 模型一致——进房烘焙一次，之后每帧只重绘，
运行时零额外开销。搬运顺序如下（全部来自 `preview.html`，函数名可直接搜）：

1. **贴图层**：`makeCanvas` → `makeFloorTexture / makeWallTexture / makeWoodTexture /
   makeMetalTexture / makeGoldTexture / makeStoneTexture` → `buildTextures()`。
   `makeCorridorTexture` 只有开门时才需要，可以不搬。
   材质名 `brass` 没有对应贴图，走 `MAT_COLOR` 的兜底色（纯色 + 明暗），这是有意的。
2. **几何层**：`addBox / addCylinder / pushFace / addShadow / addGlow`，
   以及 `project()`（唯一一处把 `z` 抬高的地方：`screenY -= z * cos52° * zoom`）。
3. **构件层**：`addCrateStack / addCrate / addBarrel / addPipeRun / addWorkbench /
   addRubble / addToolbox / addBrokenPillar / addCabinet / addBrazier / addAltar`，
   加上 `buildStairs(x0, yFront)`。
4. **布局层**：`LAYOUTS.start / dense / boss / bossDense`、`buildProp()`、`buildScene(kind)`。
   定版用 **`dense`（起点房）** 和 **`bossDense`（首领房）**。
5. **渲染层**：`viewFor()` → `renderNew()`（内部依次 `drawBackground / drawFloor /
   drawFace（按平均 y 排序）/ drawShadow / drawRune / drawGlows / drawWallAO /
   drawDoorSpills / drawVignette`）。

**主文件里怎么调用**：房间烘焙时

```js
// 伪代码：在 bakeScene 的房间分支里
const scene = buildScene(room.type === 'boss' ? 'bossDense' : 'dense');
// 用房间左上角做平移，把 1216×896 的世界坐标对到 room.x / room.y
const v = viewFor(roomCtx, room.x + 608, room.y + 448, cameraZoom(), room.w, room.h);
renderNew(roomCtx, v, scene);
```

> 注意：`LAYOUTS` 的坐标是写死在 1216×896 里的。如果某间房实际不是 1216×896
> （区间是 960–1376 × 768–1056），要么按 `room.w / 1216` 给布点做一次缩放，
> 要么把边角件按"贴墙距离"重新摆。简单做法：只做 1216×896 一档，
> 让 `paintRoom` 在别的尺寸上退回旧画法。

### 路线 B：预烘焙 PNG（最省事，但只能当静态底图）

把 `final_start_25.png` / `final_boss_25.png` 当房间底图 1:1 `drawImage`。

- 优点：零移植成本，贴图体积 = 542 KB / 555 KB。
- 缺点：① 只有 1216×896 一档，别的房间尺寸会拉伸；
  ② 装饰成了"画上去的"，不能单独遮挡玩家、不能做互动/破坏；
  ③ 两间房长得一模一样（固定布局），没有随机性。
- 结论：适合先"看效果"，不适合当正式方案。

**推荐 A**。A 的主文件增量 ≈ 1 个 `<script>` 段落 + 烘焙时一次调用，
贴图体积与 B 无关（都是运行时生成，不占包体）。

## 5. 定版数字（全部实测，游戏内帧率未测）

| 指标 | 起点房 25 件 | 首领房 25 件 | 怎么量的 |
| --- | --- | --- | --- |
| 三角面 | **1686** | **1654** | `?dump=stats` → 面点数 − 2 累加 |
| 软阴影 | 28 | 28 | 同上 |
| 发光点 | 0 | 4（双火盆 + 楼梯 + 祭坛） | 同上 |
| 屏幕占地 | 1034×762 = 787,908 px² | 同 | 1216×896 × 0.85 |
| 每件平均间隔 | **177 px** | **177 px** | `√(787,908 ÷ 25)` |
| 原 760×560 / 10 件 | 175 px | — | `√(646×476 ÷ 10)` |
| 可走面积 | **93.14%** | 同 | `(1216−36)×(896−36) ÷ (1216×896)` |
| 可走面积 / 件 | 171 px | 171 px | `√(1,014,800 ÷ 25) × 0.85` |
| 贴图 | 4612 KB raw / ≈1301 KB PNG | 同 | 见第 2 节 |
| 单帧绘制 | **未定口径** | 未定口径 | 25 件在 `?dump=stats` 里单独测到 18.5–40.8 ms，同一配置两次差 2 倍（headless 冷启动 + GC 抖动），**不可作为口径，更不是帧率**。README 的 2.5–5.8 ms 是起点房 10 件（870 面）的数 |

**结论（一句话）**：25 件摊到 787,908 px² 的屏幕上，**每件平均 177px**，
和原来 760×560 房 10 件的 **175px** 只差 **1.2%**——不会更空；同时件全部贴墙、
中心留空，可走面积仍是 **93.14%**，所以也不会更挤；南墙 **y ≥ 830 不刷怪**这条
继续成立（当前最靠南的碎石到 y ≈ 826 为止）。

## 6. 边界（别踩）

1. **`index_arcane_v2.html` 本清单一个字没写**，接入由主文件那条线执行。
2. **门洞代码不许删**：`SHOW_DOORS = false` 只是开关，改回 `true` 就能恢复
   切墙、门柱、门洞光溢出、走廊（见 README 第 10 节）。
3. **左右墙内侧面不存在**（投影只抬 z、不切 x），接入后别期待看到内侧墙面。
4. **南墙不可见带**是物理结果（62 高 × cot52° ≈ 48px），不是 bug；靠它改刷怪，
   不要去改墙高。
5. 复现出图：`preview.html?shot=final-start` / `?shot=final-boss`，
   窗口锁 `1120×880`、`--force-device-scale-factor=1`，才是 1:1。
